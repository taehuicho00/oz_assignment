## 1. Web

### 1-1. Web의 기원과 정의

**비유로 먼저**: 웹(Web)은 '거미줄'이라는 뜻이다. 전 세계에 흩어진 문서들이 **링크라는 실**로 서로 이어져 있는 모습이라 이런 이름이 붙었다.

**정의**
- 웹(WWW, World Wide Web)은 **인터넷 위에서 동작하는 정보 공유 시스템**이다.
- 문서(웹 페이지)들이 **하이퍼링크**(클릭하면 다른 문서로 이동하는 연결)로 이어져 있다.
- 웹은 아래 3가지 기술로 이루어진다.

| 기술 | 역할 | 비유 |
|---|---|---|
| URL | 자원(문서·이미지 등)이 어디 있는지 나타내는 주소 | 집 주소 |
| HTTP | 클라이언트와 서버가 자원을 주고받는 통신 규칙 | 택배 배송 규칙 |
| HTML | 웹 문서의 구조를 표현하는 언어 | 문서의 뼈대 |

**기원**
- 1989년, 유럽입자물리연구소(CERN)의 **팀 버너스리(Tim Berners-Lee)** 가 연구자들이 문서를 쉽게 공유할 수 있는 하이퍼텍스트 시스템을 제안했다.
- 1990년 말 최초의 웹 서버와 웹 브라우저(WorldWideWeb)를 만들었고, 1991년 CERN 밖으로 공개했다.
- 1993년 CERN이 웹 기술을 누구나 무료로 쓰도록 공개하면서 웹이 빠르게 퍼졌다.
- 1994년 웹 표준을 정하는 단체 **W3C**가 설립되었다.

**인터넷과 웹은 다르다 (자주 헷갈리는 부분)**
- **인터넷**: 전 세계 컴퓨터를 연결한 **네트워크 자체(도로망)**. 1969년 미국의 ARPANET에서 출발했다.
- **웹**: 인터넷이라는 도로 위에서 돌아가는 **서비스 중 하나(택배 서비스)**. 이메일, 파일 전송(FTP), 온라인 게임도 인터넷 위의 다른 서비스다.

### 1-2. Web Service의 개념

**비유**: 식당. 손님(브라우저)이 메뉴를 주문(요청)하면, 주방(서버)이 음식을 만들어 내준다(응답).

- **웹 서비스**: 웹 기술(HTTP, HTML 등)을 이용해 사용자에게 정보나 기능을 제공하는 서비스. 예) 포털 검색, 유튜브, 온라인 쇼핑몰, 병원 예약 사이트
- 좁은 의미로는 **프로그램과 프로그램이 HTTP로 데이터를 주고받는 방식**을 뜻하기도 한다. W3C는 웹 서비스를 "네트워크에서 기계와 기계 사이의 상호작용을 지원하도록 설계된 소프트웨어 시스템"으로 정의한다. (→ 3장의 API와 연결)

**정적 웹 vs 동적 웹**

| 구분 | 정적(Static) 웹 | 동적(Dynamic) 웹 |
|---|---|---|
| 응답 방식 | 미리 만들어 둔 파일(HTML·CSS·이미지)을 그대로 전달 | 요청이 올 때마다 서버가 코드 실행·DB 조회로 결과를 만들어 전달 |
| 내용 | 누가 접속해도 같음 | 사용자·시간·조건에 따라 달라짐 |
| 예시 | 회사 소개 페이지, 내 이력서 페이지 | 로그인 후 내 피드, 검색 결과, 장바구니 |

### 1-3. 웹 서비스 흐름 정리

주소창에 `https://www.example.com/index.html`을 입력하고 Enter를 누르면 이런 일이 일어난다.

```
[브라우저]                                         [DNS 서버]
   |  (1) "www.example.com의 IP 주소가 뭐야?"  -------->|
   |<-------- (2) "203.0.113.10 이야" (예시 주소) ------|
   |
   |  (3) 서버와 TCP 연결 (HTTPS라면 TLS 핸드셰이크까지)
   |  (4) HTTP 요청: GET /index.html  ------>  [웹 서버] --> [애플리케이션 서버] --> [DB]
   |                                          (Nginx 등)   (코드 실행)
   |<------ (5) HTTP 응답: 200 OK + HTML ------
   |
   (6) HTML 해석 -> CSS·JS·이미지 추가 요청 -> 화면에 그리기(렌더링)
```

1. 사용자가 URL을 입력한다.
2. **DNS 조회**: 도메인 이름을 IP 주소로 바꾼다. (2일차 DNS 참고)
3. 서버와 **TCP 연결**을 맺는다. HTTPS라면 **TLS 핸드셰이크**로 암호화 준비를 한다.
4. 브라우저가 **HTTP 요청**을 보낸다.
5. 서버가 처리한다. 정적 파일은 웹 서버가 바로 돌려주고, 동적 처리는 애플리케이션 서버가 코드를 실행하고 DB를 조회해 결과를 만든다.
6. 브라우저가 **HTTP 응답**을 받아 HTML을 해석(파싱)하고, 필요한 CSS·JS·이미지를 추가로 요청한 뒤 화면에 그린다.

**웹 서버 vs WAS(애플리케이션 서버)**

| 구분 | 웹 서버 (Web Server) | WAS (Web Application Server) |
|---|---|---|
| 하는 일 | 정적 파일 제공, 요청을 뒤쪽 서버로 전달(리버스 프록시), HTTPS 처리 | 프로그램 코드를 실행해 동적인 결과를 만들고 DB와 연동 |
| 예시 | Nginx, Apache HTTP Server | Java의 Tomcat. Python에서는 Uvicorn·Gunicorn 같은 애플리케이션 서버가 FastAPI·Django 코드를 실행 |

> 왜 나눌까? 정적 파일 전달은 웹 서버가 훨씬 빠르게 처리하고, 무거운 계산은 애플리케이션 서버에 맡기면 서버 자원을 효율적으로 쓸 수 있기 때문이다.

### 1-4. 용어 정리

| 용어 | 뜻 | 예시 |
|---|---|---|
| 인터넷 (Internet) | 전 세계 네트워크를 연결한 '네트워크의 네트워크' | 집 공유기 → 통신사 → 해외 서버 |
| 웹 (WWW) | 인터넷 위에서 동작하는 하이퍼텍스트 정보 공유 서비스 | 웹 사이트들 |
| 클라이언트 (Client) | 요청을 보내는 쪽 | 브라우저, 모바일 앱, curl |
| 서버 (Server) | 요청을 받아 처리하고 응답하는 쪽 | 웹 서버, API 서버 |
| 브라우저 (Browser) | 웹 페이지를 요청하고 화면에 그려주는 프로그램 | Chrome, Safari, Edge |
| URL | 자원의 위치를 나타내는 주소 | 아래 'URL 뜯어보기' 참고 |
| 도메인 (Domain) | 사람이 기억하기 쉬운 서버 이름 | naver.com |
| IP 주소 | 네트워크에서 기기를 구분하는 숫자 주소 | 203.0.113.10 (문서용 예시 주소) |
| DNS | 도메인을 IP 주소로 바꿔 주는 시스템 | 인터넷 전화번호부 |
| 포트 (Port) | 한 컴퓨터 안에서 어떤 프로그램에 전달할지 구분하는 번호 | HTTP 80, HTTPS 443 |
| HTTP / HTTPS | 웹 통신 규칙 / 그 통신을 암호화한 것 | `http://`, `https://` |
| HTML / CSS / JavaScript | 구조 / 꾸밈 / 동작 | 집의 뼈대 / 인테리어 / 전기 배선 |
| 프론트엔드 / 백엔드 | 사용자가 보는 화면 쪽 개발 / 서버·DB 쪽 개발 | React / FastAPI |
| 요청 (Request) / 응답 (Response) | 클라이언트가 보내는 메시지 / 서버가 돌려주는 메시지 | GET 요청 / 200 OK 응답 |
| API | 프로그램끼리 소통하기 위한 약속된 창구 | 시세 조회 API |
| 렌더링 (Rendering) | 받은 HTML·CSS·JS를 해석해 화면에 그리는 과정 | 페이지가 '그려지는' 순간 |

**URL 뜯어보기**: `https://www.example.com:443/search?q=python&page=2#result`

| 부분 | 이름 | 의미 |
|---|---|---|
| `https` | 스킴(scheme) | 어떤 규칙(프로토콜)으로 통신할지 |
| `www.example.com` | 호스트(도메인) | 어느 서버인지 |
| `443` | 포트 | 서버의 몇 번 문으로 들어갈지 (https 기본값이라 보통 생략) |
| `/search` | 경로(path) | 서버 안의 어떤 자원인지 |
| `?q=python&page=2` | 쿼리 스트링 | 추가 조건 (2일차 Query Parameter) |
| `#result` | 프래그먼트 | 페이지 안의 위치. **서버로는 전송되지 않는다** |

## 2. HTTP

### 2-1. Client - Server 모델 정리

**비유**: 손님과 식당. 대화는 항상 **손님(클라이언트)이 먼저 주문(요청)** 하고, 식당(서버)은 **주문에 답(응답)** 한다. 식당이 먼저 손님 집에 음식을 보내지 않는다.

- **정의**: 서비스를 **요청하는 쪽(클라이언트)** 과 **제공하는 쪽(서버)** 으로 역할을 나눈 구조.
- **장점**
  - 역할이 나뉘어 화면(프론트엔드)과 서버(백엔드)를 따로 개발·수정할 수 있다.
  - 데이터를 서버에서 한곳에 관리하므로 모든 사용자가 같은 최신 데이터를 본다.
  - 서버 하나가 웹·앱 같은 여러 클라이언트에 동시에 서비스할 수 있다.
- **단점·주의**
  - 사용자가 몰리면 서버에 부하가 생긴다 → 서버 대수를 늘리고(스케일 아웃) 로드밸런서로 요청을 나눈다.
  - 서버가 멈추면 모든 클라이언트가 영향을 받는다.
- **HTTP에서의 특징**
  - **무상태(Stateless)**: 서버는 이전 요청을 기억하지 않는다. 그래서 로그인 상태를 유지하려면 쿠키·세션·토큰을 쓴다.
  - **요청 1개 → 응답 1개**: 서버가 먼저 데이터를 밀어주려면(실시간 채팅 등) WebSocket 같은 별도 기술이 필요하다.

### 2-2. HTTP란?

- **HTTP(HyperText Transfer Protocol)**: 웹에서 HTML 문서, 이미지, JSON 데이터 같은 **자원(resource)을 주고받기 위한 통신 규약**.
- **프로토콜(Protocol)**: 서로 다른 컴퓨터가 대화하기 위한 공통 규칙. 사람으로 치면 '같은 언어 + 대화 예절'.
- 주로 **TCP** 위에서 동작한다. (HTTP/3는 UDP 기반의 QUIC 위에서 동작)
- 기본 포트: HTTP **80**, HTTPS **443**

| 버전 | 표준화 | 핵심 변화 |
|---|---|---|
| HTTP/1.0 | 1996 | 요청마다 연결을 새로 맺는 것이 기본 |
| HTTP/1.1 | 1997 | 연결 재사용(keep-alive)이 기본, `Host` 헤더 필수. 지금도 널리 쓰임 |
| HTTP/2 | 2015 | 한 연결로 여러 요청을 동시에 처리(멀티플렉싱), 헤더 압축 |
| HTTP/3 | 2022 | TCP 대신 QUIC 사용 → 연결이 더 빠르고 손실에 강함 |

**HTTP 메서드** (요청의 목적): `GET`(조회), `POST`(생성), `PUT`(전체 수정), `PATCH`(부분 수정), `DELETE`(삭제). 그 밖에 `HEAD`(바디 없이 헤더만 조회), `OPTIONS`(가능한 통신 옵션 확인)

**상태 코드** (응답 결과를 숫자 3자리로 요약)

| 범위 | 의미 | 자주 보는 코드 |
|---|---|---|
| 1xx | 정보 | 101 Switching Protocols |
| 2xx | 성공 | 200 OK, 201 Created, 204 No Content |
| 3xx | 리다이렉션(다른 곳으로 가라) | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | 클라이언트 쪽 문제 | 400 Bad Request, 401 Unauthorized(인증 필요), 403 Forbidden(권한 없음), 404 Not Found, 405 Method Not Allowed, 422 Unprocessable Content(형식은 맞지만 값 검증 실패) |
| 5xx | 서버 쪽 문제 | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

### 2-3. HTTP 메시지의 구성

**비유**: 편지 = 봉투 겉면(시작줄 + 헤더) + 한 줄 띄우기 + 편지 내용(바디)

**요청 메시지 (Request)**

```
POST /patients HTTP/1.1           <- (1) 시작줄: 메서드 + 요청 대상(경로) + HTTP 버전
Host: 127.0.0.1:8000              <- (2) 헤더: "이름: 값" 형태의 부가 정보
User-Agent: curl/8.5.0
Accept: */*
Content-Type: application/json
Content-Length: 24
                                  <- (3) 빈 줄: "헤더 끝!" 표시
{"name":"jung","age":33}          <- (4) 바디(본문): 보낼 데이터 (GET은 보통 없음)
```

**응답 메시지 (Response)**

```
HTTP/1.1 201 Created              <- (1) 상태줄: HTTP 버전 + 상태 코드 + 상태 메시지
date: Mon, 09 Nov 2026 09:20:03 GMT   <- (2) 헤더
server: uvicorn
content-length: 31
content-type: application/json
                                  <- (3) 빈 줄
{"id":3,"name":"jung","age":33}   <- (4) 바디
```

- 헤더 이름은 **대소문자를 구분하지 않는다.** 위 응답처럼 소문자로 보내는 서버도 있다.
- `Content-Type`은 바디의 형식(JSON, HTML 등), `Content-Length`는 바디의 크기(바이트)를 알려준다.

### 2-4. Curl 을 활용한 HTTP 요청 예제

- **curl(Client URL)**: 터미널에서 HTTP 요청을 직접 보내 보는 도구. macOS·Linux에 기본으로 있고 Windows 10 이상에도 들어 있다. (Windows PowerShell에서는 `curl`이 다른 명령의 별칭일 수 있어 `curl.exe`로 실행하는 것이 안전)

| 옵션 | 뜻 |
|---|---|
| (옵션 없음) | GET 요청, 응답 바디만 출력 |
| `-i` | 응답 **헤더까지** 출력 |
| `-I` | HEAD 요청 (헤더만 받기) |
| `-v` | 요청·응답 과정을 자세히 출력 (`>` 보낸 내용, `<` 받은 내용) |
| `-X 메서드` | 메서드 지정 (POST, PUT, DELETE …) |
| `-H "이름: 값"` | 요청 헤더 추가 |
| `-d '데이터'` | 바디 전송 (지정하면 메서드가 자동으로 POST) |

아래는 FastAPI로 만든 실습용 미니 서버(`http://127.0.0.1:8000`)에 실제로 요청한 결과다.

**(1) 목록 조회 - GET**
```bash
$ curl -i http://127.0.0.1:8000/patients
HTTP/1.1 200 OK
date: Mon, 09 Nov 2026 09:19:55 GMT
server: uvicorn
content-length: 63
content-type: application/json

[{"id":1,"name":"kim","age":30},{"id":2,"name":"lee","age":45}]
```

**(2) 생성 - POST + JSON 바디**
```bash
$ curl -i -X POST http://127.0.0.1:8000/patients \
    -H "Content-Type: application/json" \
    -d '{"name":"park","age":27}'
HTTP/1.1 201 Created
date: Mon, 09 Nov 2026 09:19:55 GMT
server: uvicorn
content-length: 31
content-type: application/json

{"id":3,"name":"park","age":27}
```

**(3) 없는 자원 - 404**
```bash
$ curl -i http://127.0.0.1:8000/patients/99
HTTP/1.1 404 Not Found
...
{"detail":"Patient not found"}
```

**(4) 값이 잘못됨 - 422** (나이에 숫자 대신 글자를 보냄)
```bash
$ curl -i -X POST http://127.0.0.1:8000/patients \
    -H "Content-Type: application/json" \
    -d '{"name":"choi","age":"thirty"}'
HTTP/1.1 422 Unprocessable Content
...
{"detail":[{"type":"int_parsing","loc":["body","age"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"thirty"}]}
```

**(5) 삭제 - DELETE**
```bash
$ curl -i -X DELETE http://127.0.0.1:8000/patients/3
HTTP/1.1 204 No Content
date: Mon, 09 Nov 2026 09:19:55 GMT
server: uvicorn
```

**(6) `-v`로 내가 보낸 요청까지 보기**

## 3. RestAPI

### 3-1. URL과 HTTP Method로 요청의 의도를 나타내는 방법

**핵심 한 줄**: **URL은 '무엇을'(자원, 명사), 메서드는 '어떻게'(행위, 동사)**

**비유**: 도서관에서 '책'(자원)은 그대로이고, '빌린다·반납한다·찾는다'(행위)만 바뀐다. URL에는 책 이름만 적고, 행위는 메서드로 말한다.

| 의도 | 나쁜 예 (URL에 동사) | 좋은 예 (REST 방식) |
|---|---|---|
| 환자 목록 조회 | `GET /getPatients` | `GET /patients` |
| 환자 등록 | `POST /createPatient` | `POST /patients` |
| 7번 환자 조회 | `GET /getPatient?id=7` | `GET /patients/7` |
| 7번 환자 수정 | `POST /updatePatient` | `PUT` 또는 `PATCH /patients/7` |
| 7번 환자 삭제 | `GET /deletePatient?id=7` | `DELETE /patients/7` |

**CRUD와 HTTP 메서드 대응표** (CRUD = Create·Read·Update·Delete, 데이터를 다루는 4가지 기본 동작)

| CRUD | 메서드 | URL 예시 | 의미 | 성공 시 주로 쓰는 코드 |
|---|---|---|---|---|
| Create | POST | `/patients` | 새 환자 등록 | 201 Created |
| Read | GET | `/patients`, `/patients/7` | 목록 조회 / 단건 조회 | 200 OK |
| Update | PUT | `/patients/7` | 자원 **전체**를 교체 | 200 OK 또는 204 |
| Update | PATCH | `/patients/7` | 자원 **일부**만 수정 | 200 OK |
| Delete | DELETE | `/patients/7` | 삭제 | 204 No Content (또는 200) |

**URL 설계 규칙**
- 자원은 **명사**, 보통 **복수형**으로 쓴다: `/patients`
- 계층 관계는 슬래시로 표현한다: `/patients/7/records` (7번 환자의 진료 기록)
- **소문자**를 쓰고, 단어 연결은 **하이픈(-)** 을 쓴다: `/medical-records` (언더바는 피함)
- 끝에 슬래시(`/`)나 파일 확장자(`.json`)를 붙이지 않는다.
- 필터·정렬·페이지는 **쿼리 스트링**으로: `/patients?ward=3&sort=name&page=2`

**안전(Safe)과 멱등(Idempotent)**
- 안전: 서버의 데이터를 바꾸지 않는 메서드 → `GET`, `HEAD`, `OPTIONS`
- 멱등: 같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같은 메서드 → `GET`, `PUT`, `DELETE`
  - `POST`는 멱등이 아니다 (두 번 보내면 환자가 2명 생김). `PATCH`도 멱등이 보장되지 않는다.
- 왜 중요할까? 네트워크 오류로 요청을 **재시도**할 때, 멱등한 요청은 다시 보내도 안전하다.

#### 예외 케이스

CRUD 4가지로 딱 떨어지지 않는 '행위'도 있다. 이럴 때는 **동사 성격의 하위 경로**를 쓰는 것이 일반적이다.
원칙: 먼저 '자원 + 메서드'로 표현해 보고, 정말 어려울 때만 예외를 쓰되 **팀 안에서 규칙을 통일**한다.

| 상황 | 예시 | 이유 |
|---|---|---|
| 로그인·로그아웃 | `POST /auth/login`, `POST /auth/logout` | 특정 자원의 CRUD라기보다 '인증'이라는 행위 |
| 상태를 바꾸는 행위 | `POST /orders/12/cancel` | 취소는 환불 등 여러 처리가 따라오는 행위 (`PATCH /orders/12`에 `{"status":"cancelled"}`로 표현하기도 함) |
| 여러 자원을 가로지르는 검색 | `GET /search?q=pneumonia` | 한 종류의 자원이 아님 |
| 조회지만 조건이 매우 복잡함 | `POST /patients/search` (조건을 바디에 담음) | GET 요청의 바디는 의미가 정해져 있지 않아 쓰지 않는 것이 원칙이고, URL 길이에도 한계가 있음 |
| 여러 개를 한 번에 처리 | `POST /patients/bulk-delete` | 일괄 처리 |
| 메일 발송 같은 동작 | `POST /users/7/password-reset` | '보낸다'는 행위 |

### 3-2. API 란?

- **API(Application Programming Interface)**: 프로그램끼리 기능이나 데이터를 주고받기 위해 **미리 약속해 둔 창구**.
- **비유**: 식당의 메뉴판과 주문 창구. 주방(서버 내부)이 어떻게 요리하는지 몰라도, 메뉴판(API 문서)에 적힌 대로 주문(요청)하면 음식(응답)이 나온다.
- **예시**
  - 웹 API: 바이낸스 시세 API `GET https://api4.binance.com/api/v3/ticker/24hr` (JavaScript 3일차 과제에서 사용), 날씨 API, 지도 API
  - 라이브러리 API: pandas의 `pd.read_csv()`, `df.groupby()`도 '이렇게 부르면 이렇게 동작한다'는 약속이므로 API다.
- **왜 쓸까?** 남이 만든 기능을 내부 구현을 몰라도 재사용할 수 있고, 웹·모바일 앱이 같은 서버를 함께 쓸 수 있다.
- **API 문서**: 어떤 URL·메서드·파라미터를 쓰는지 적은 설명서. FastAPI는 `/docs` 주소에 문서(Swagger UI)를 자동으로 만들어 준다.

### 3-3. RestAPI 정의

- **REST(REpresentational State Transfer)**: 2000년 로이 필딩(Roy Fielding)이 박사 논문에서 정리한 **웹 아키텍처 스타일**(설계 원칙의 모음). 공식 규격이 아니라 '스타일'이다.
- **REST API(RESTful API)**: REST 원칙을 지켜서 만든 웹 API.

**REST의 3요소**

| 요소 | 의미 | 예 |
|---|---|---|
| 자원 (Resource) | URI로 식별되는 대상 | `/patients/7` |
| 행위 (Verb) | HTTP 메서드 | GET, POST, PUT, PATCH, DELETE |
| 표현 (Representation) | 자원을 주고받는 형태 | JSON `{"id":7,"name":"kim"}` |

**REST의 제약 조건 6가지**
- **Client-Server**: 클라이언트와 서버의 역할을 분리한다.
- **Stateless**: 각 요청이 처리에 필요한 정보를 모두 담는다. 서버는 이전 요청을 기억하지 않는다.
- **Cacheable**: 응답에 캐시해도 되는지 표시할 수 있어야 한다.
- **Uniform Interface**: 일관된 방식으로 소통한다 (URI로 자원 식별, 메서드로 조작, 메시지만 보고도 의미를 알 수 있게 등).
- **Layered System**: 중간에 프록시·로드밸런서 같은 계층이 있어도 클라이언트는 신경 쓰지 않아도 된다.
- **Code on Demand (선택)**: 서버가 실행할 코드(JavaScript 등)를 내려줄 수 있다.

**장점과 단점**
- 장점: HTTP를 그대로 활용해 배우기 쉽고, URL과 메서드만 봐도 의도를 알 수 있다. 프론트엔드·백엔드 분리에 유리하다.
- 단점: 공식 표준이 없어 팀마다 설계가 조금씩 다르고, CRUD로 표현하기 어려운 행위가 있다(→ 예외 케이스).

**FastAPI 코드로 보면** (`PatientIn`, `PatientUpdate`는 요청 바디 형식을 정의한 Pydantic 모델)

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/patients")                                    # Read: 목록 조회
def list_patients(): ...

@app.get("/patients/{patient_id}")                       # Read: 단건 조회
def get_patient(patient_id: int): ...

@app.post("/patients", status_code=201)                  # Create: 생성
def create_patient(body: PatientIn): ...

@app.patch("/patients/{patient_id}")                     # Update: 부분 수정
def update_patient(patient_id: int, body: PatientUpdate): ...

@app.delete("/patients/{patient_id}", status_code=204)   # Delete: 삭제
def delete_patient(patient_id: int): ...
```

URL(`/patients/{patient_id}`)은 그대로 두고 데코레이터의 메서드(`get`, `post`, `patch`, `delete`)만 바꿔서 의도를 표현하는 것이 REST 방식의 핵심이다.

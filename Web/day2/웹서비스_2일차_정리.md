## 1. HTTP 요청 방법

클라이언트가 서버에 정보를 실어 보낼 수 있는 자리는 크게 3곳이다.
택배에 비유하면 **Query Parameter = 상자 겉면 메모**, **Request Body = 상자 안 내용물**, **Header = 송장(배송 정보)** 이다.

```
POST /patients?notify=true HTTP/1.1     <- Query Parameter (URL의 ? 뒤)
Host: api.example.com                   <- Header
Content-Type: application/json          <- Header
Authorization: Bearer <토큰>             <- Header

{"name":"kim","age":30}                 <- Request Body
```

### Query Parameter

- **정의**: URL의 `?` 뒤에 `키=값` 쌍을 `&`로 이어 붙인 것. 이 부분 전체를 쿼리 스트링(query string)이라고 한다.
- **주 용도**: 조회(GET)할 때의 **검색어, 필터, 정렬, 페이지 번호**
- **특징**
  - URL에 그대로 보이므로 브라우저 기록·서버 로그에 남는다 → **비밀번호·개인정보는 절대 넣지 않는다.**
  - 한글·공백 같은 문자는 **퍼센트 인코딩**되어 전송된다. 예) `폐렴` → `%ED%8F%90%EB%A0%B4`
  - HTTP 표준에 URL 길이의 고정 상한은 없지만 브라우저·서버마다 제한이 있으므로 긴 데이터는 바디로 보낸다.
- **Path Parameter와의 차이**
  - `/patients/7` → 경로 자체로 **특정 자원 하나를 식별** (Path Parameter)
  - `/patients?ward=3` → 목록을 **조건으로 거름** (Query Parameter)

### Query Parameter의 사용예시

```
GET /patients?ward=3&sort=name&page=2&size=20     # 3병동 환자를 이름순으로, 2페이지(20명씩)
https://www.google.com/search?q=fastapi           # 검색어
https://www.youtube.com/watch?v=<영상ID>           # 볼 영상 지정
https://api4.binance.com/api/v3/ticker/24hr?symbol=BTCUSDT   # 특정 코인 시세만 조회
```

실습 서버에 실제로 요청한 결과 (나이 40 이상만 필터):

```bash
$ curl -i "http://127.0.0.1:8000/patients?min_age=40"
HTTP/1.1 200 OK
date: Mon, 09 Nov 2026 09:19:55 GMT
server: uvicorn
content-length: 32
content-type: application/json

[{"id":2,"name":"lee","age":45}]
```

> 쉘에서는 `&`가 특별한 의미(백그라운드 실행)를 가지므로, 쿼리가 있는 URL은 **따옴표로 감싼다.**

JavaScript에서 쿼리 스트링 만들기 (인코딩을 자동으로 해 준다):
```js
const params = new URLSearchParams({ q: "폐렴", page: 2 });
console.log(params.toString());   // q=%ED%8F%90%EB%A0%B4&page=2
```

FastAPI에서는 경로에 없는 함수 매개변수가 자동으로 쿼리 파라미터가 된다:
```python
@app.get("/patients")
def list_patients(min_age: int = 0):   # /patients?min_age=40
    ...
```

### Request Body

- **정의**: HTTP 메시지에서 **빈 줄 다음에 오는 본문 데이터**. 주로 `POST`, `PUT`, `PATCH`에서 쓴다.
- **특징**
  - 크고 복잡한 데이터(JSON, 파일 등)를 담을 수 있다.
  - URL에 보이지 않지만 **암호화되는 것은 아니다.** HTTP라면 중간에서 그대로 읽힐 수 있어 HTTPS가 필요하다.
  - `Content-Type` 헤더로 바디의 형식을 꼭 알려줘야 서버가 올바르게 해석한다.
  - `GET` 요청의 바디는 의미가 정해져 있지 않아 쓰지 않는 것이 원칙이다.

| Content-Type | 형식 | 언제 |
|---|---|---|
| `application/json` | `{"name":"kim","age":30}` | API 통신에서 가장 많이 씀 |
| `application/x-www-form-urlencoded` | `name=kim&age=30` | HTML `<form>` 기본 전송 방식 |
| `multipart/form-data` | 여러 파트로 나눠 전송 | 파일(이미지·X-ray 등) 업로드 |
| `text/plain` | 일반 텍스트 | 단순 문자열 |

### Request Body의 사용예시

실습 서버에 JSON 바디로 환자를 등록한 실제 결과 (`-v`로 보낸 내용까지 확인):

```bash
$ curl -v http://127.0.0.1:8000/patients \
    -H "Content-Type: application/json" \
    -d '{"name":"jung","age":33}'
> POST /patients HTTP/1.1
> Host: 127.0.0.1:8000
> User-Agent: curl/8.5.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 24
>
< HTTP/1.1 201 Created
< server: uvicorn
< content-length: 31
< content-type: application/json
<
{"id":3,"name":"jung","age":33}
```
- `-d`를 쓰면 curl이 자동으로 `POST`를 보낸다. 다만 기본 형식이 `application/x-www-form-urlencoded`라서 JSON을 보낼 때는 `-H "Content-Type: application/json"`을 붙인다.

JavaScript(fetch)로 같은 요청 보내기:
```js
fetch("http://127.0.0.1:8000/patients", {
  method: "POST",                                   // 메서드
  headers: { "Content-Type": "application/json" },  // 바디 형식을 알려주는 헤더
  body: JSON.stringify({ name: "jung", age: 33 }),  // 객체를 JSON 문자열로 바꿔 바디에 담음
})
  .then((res) => res.json())     // 응답 바디(JSON)를 객체로 변환
  .then((data) => console.log(data));
```

HTML 폼은 기본적으로 `application/x-www-form-urlencoded` 형식으로 바디를 보낸다:
```html
<form action="/patients" method="post">
  <input name="name" value="kim">
  <input name="age" value="30">
  <button type="submit">등록</button>   <!-- 전송 시 바디: name=kim&age=30 -->
</form>
```

### Header

- **정의**: `이름: 값` 형태로 요청·응답에 붙는 **부가 정보(메타데이터)**. 택배의 송장처럼 '누가, 어떤 형식으로, 어떤 조건으로' 보내는지 알려준다.
- 헤더 이름은 대소문자를 구분하지 않는다.

| 구분 | 헤더 | 의미 |
|---|---|---|
| 요청 | `Host` | 요청 대상 서버 (HTTP/1.1에서 필수) |
| 요청 | `User-Agent` | 요청을 보낸 프로그램 정보 (브라우저 종류 등) |
| 요청 | `Accept` | 받고 싶은 응답 형식 (`application/json` 등) |
| 요청 | `Accept-Language` | 선호하는 언어 (`ko-KR,ko;q=0.9`) |
| 요청 | `Authorization` | 인증 정보 (토큰 등) |
| 요청 | `Cookie` | 브라우저가 저장해 둔 쿠키 |
| 요청 | `Origin` | 요청을 보낸 페이지의 출처 (CORS 판단에 사용) |
| 공통 | `Content-Type` / `Content-Length` | 바디의 형식 / 크기(바이트) |
| 응답 | `Set-Cookie` | 브라우저에 쿠키 저장 요청 |
| 응답 | `Location` | 리다이렉트할 주소, 새로 만든 자원의 위치 |
| 응답 | `Cache-Control` | 캐시 정책 (얼마나 저장해도 되는지) |
| 응답 | `Access-Control-Allow-Origin` | 다른 출처의 요청을 허용하는지 (CORS) |

### Header의 사용예시

- **인증**: 로그인 후 받은 토큰을 매 요청에 실어 보낸다 → `Authorization: Bearer <토큰>`
- **언어 선택**: `Accept-Language: ko-KR` → 다국어 서비스가 한국어 응답을 고를 수 있다.
- **응답 형식 협상**: `Accept: application/json` → JSON으로 달라고 요청
- **캐시 활용**: 서버가 준 `ETag` 값을 `If-None-Match`에 넣어 보내면, 바뀐 게 없을 때 서버가 `304 Not Modified`만 돌려줘 데이터를 아낀다.

실습 서버에 헤더를 직접 넣어 보낸 실제 결과 (서버가 받은 헤더 값을 그대로 돌려주는 `/me` 엔드포인트):
```bash
$ curl -i http://127.0.0.1:8000/me \
    -H "Authorization: Bearer test-token-123" \
    -H "Accept-Language: ko-KR,ko;q=0.9"
HTTP/1.1 200 OK
date: Mon, 09 Nov 2026 09:20:03 GMT
server: uvicorn
content-length: 76
content-type: application/json

{"authorization":"Bearer test-token-123","accept_language":"ko-KR,ko;q=0.9"}
```

JavaScript에서는 `fetch(url, { headers: { Authorization: "Bearer " + token } })`처럼 보낸다.

## 2. HTTPS

### HTTPS 의 정의

- **HTTPS(HTTP Secure)**: HTTP 메시지를 **TLS(Transport Layer Security)** 로 암호화해서 주고받는 방식. 기본 포트는 **443**.
- **비유**: HTTP는 **엽서**(배달하는 사람 누구나 읽을 수 있음), HTTPS는 **자물쇠 달린 상자 + 받는 사람 신분증 확인**.
- HTTPS가 보장하는 3가지

| 보장 | 의미 | 막아 주는 것 |
|---|---|---|
| 기밀성 | 내용을 암호화 | 중간에서 엿보기 (공용 와이파이 도청 등) |
| 무결성 | 내용이 바뀌면 알아챔 | 중간에서 내용 바꿔치기 |
| 인증 | 접속한 서버가 진짜인지 확인 (인증서) | 가짜 사이트로 유도하기 |

- **SSL vs TLS**: SSL은 TLS의 옛 이름(전신)이다. SSL 2.0·3.0은 보안 문제로 폐기되었고, 지금은 TLS 1.2와 TLS 1.3을 쓴다. 다만 'SSL 인증서'라는 이름은 관습적으로 계속 쓰인다.
- **주의**: HTTPS여도 **접속한 도메인 이름과 IP 주소는 노출될 수 있다.** 암호화되는 것은 URL 경로·쿼리, 헤더, 바디 같은 HTTP 메시지 내용이다.

### TLS 핸드셰이크

본격적으로 데이터를 보내기 전에, 클라이언트와 서버가 **악수(handshake)하며 세 가지를 합의**하는 과정이다.
1. 어떤 암호 방식을 쓸지 정하기
2. 서버가 진짜인지 **인증서로 확인**하기
3. 실제 데이터를 암호화할 **대칭키(세션 키)를 안전하게 나눠 갖기**

**왜 대칭키와 공개키를 같이 쓸까?**

| 구분 | 대칭키 암호 | 공개키(비대칭키) 암호 |
|---|---|---|
| 방식 | 같은 키로 잠그고 연다 | 공개키로 잠근 것은 개인키로만 연다 (서명은 반대로 검증) |
| 속도 | 빠름 | 느림 |
| 약점 | 키를 상대에게 안전하게 전달하기 어려움 | 대량 데이터 암호화에 비효율적 |
| HTTPS에서 역할 | 실제 HTTP 데이터 암호화 | 키 합의와 서버 인증(서명) |

→ **느리지만 안전한 공개키 방식으로 '열쇠'를 나눈 뒤, 빠른 대칭키로 데이터를 주고받는다.**

**TLS 1.3 핸드셰이크 흐름 (현재 표준, 1번 왕복으로 끝남)**
```
클라이언트                                         서버
   | -- ClientHello --------------------------------> |  지원하는 암호 방식 목록, 랜덤 값, 키 교환용 공개 값
   | <-------------------------------- ServerHello -- |  선택한 암호 방식, 서버의 키 교환용 공개 값
   |     (여기서 양쪽이 같은 비밀값을 계산 → 이후 내용은 암호화)
   | <------- EncryptedExtensions, Certificate, ----- |  서버 인증서
   |          CertificateVerify, Finished             |  인증서의 개인키로 서명 = "내가 진짜 주인"
   |  인증서 검증 (신뢰하는 CA가 서명했나? 도메인 일치? 유효기간?)
   | -- Finished -----------------------------------> |
   | <=========== 세션 키로 암호화된 HTTP 통신 ========> |
```

로컬 HTTPS 실습 서버에 `curl -v`로 접속했을 때 실제로 찍힌 핸드셰이크 로그:
```
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* TLSv1.3 (IN), TLS handshake, Encrypted Extensions (8):
* TLSv1.3 (IN), TLS handshake, Certificate (11):
* TLSv1.3 (IN), TLS handshake, CERT verify (15):
* TLSv1.3 (IN), TLS handshake, Finished (20):
* TLSv1.3 (OUT), TLS change cipher, Change cipher spec (1):
* TLSv1.3 (OUT), TLS handshake, Finished (20):
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519 / id-ecPublicKey
* Server certificate:
*  subject: CN=localhost
*  subjectAltName: host "localhost" matched cert's "localhost"
*  SSL certificate verify ok.
> GET /patients/1 HTTP/1.1
```
- `TLS_AES_256_GCM_SHA384`: 데이터 암호화에 쓰는 대칭키 방식(AES-256-GCM)
- `X25519`: 세션 키를 만들기 위한 키 교환 방식(타원곡선 디피-헬만)
- `(OUT)`은 내가 보낸 것, `(IN)`은 서버가 보낸 것

> 참고: 교재에 자주 나오는 "클라이언트가 대칭키를 서버의 공개키로 암호화해서 보낸다"는 설명은 TLS 1.2까지 쓰이던 **RSA 키 교환** 방식이다. TLS 1.3에서는 이 방식이 빠지고, 양쪽이 공개 값을 교환해 같은 비밀값을 계산하는 **(EC)DHE 방식**만 쓴다. (TLS 1.2는 보통 2번 왕복, TLS 1.3은 1번 왕복)

### SSL 인증서

- **비유**: 서버의 **신분증**. 믿을 수 있는 발급 기관(CA)의 도장이 찍혀 있다.
- **정의**: "이 공개키의 주인은 example.com이다"라는 정보를 **인증기관(CA, Certificate Authority)** 이 전자서명한 디지털 문서. 표준 형식은 X.509.
- **담긴 정보**: 도메인 이름, 발급자(CA), 유효기간, 서버의 공개키, CA의 전자서명
- **신뢰 체인 (Chain of Trust)**
  ```
  루트 CA 인증서   ← 브라우저·운영체제에 미리 내장되어 있음
      | 서명
  중간 CA 인증서
      | 서명
  서버 인증서 (example.com)
  ```
  브라우저는 서버 인증서의 서명을 따라 올라가 **내가 믿는 루트 CA**까지 닿으면 신뢰한다.
- **검증 수준에 따른 종류**: DV(도메인 소유만 확인), OV(조직 실체까지 확인), EV(가장 엄격한 확인)
- 인증서에는 유효기간이 있어 만료 전에 갱신해야 한다. 요즘은 **Let's Encrypt**처럼 무료 인증서를 자동으로 발급·갱신하는 방식이 많이 쓰인다.
- 위 실습처럼 스스로 서명한 인증서(Self-signed)는 브라우저가 믿지 않아 경고 화면이 뜬다. (실습에서는 `--cacert`로 직접 신뢰를 지정함)

### HTTPS 동작 방식

```
(1) DNS 조회        www.example.com -> IP 주소
(2) TCP 연결        443번 포트로 3-way handshake (SYN -> SYN/ACK -> ACK)
(3) TLS 핸드셰이크   암호 방식 합의 + 인증서 검증 + 세션 키 생성
(4) 암호화된 HTTP    세션 키(대칭키)로 요청·응답을 암호화해서 주고받음
(5) 연결 재사용/종료  keep-alive로 연결 유지, 또는 종료
```
- `http://`로 접속하면 서버가 `301` 리다이렉트로 `https://`로 보내는 경우가 많다.
- 서버가 `Strict-Transport-Security`(HSTS) 헤더를 보내면, 브라우저는 그 사이트에 앞으로 HTTPS로만 접속한다.
- 주소창의 자물쇠 아이콘을 누르면 인증서 정보(발급자, 유효기간)를 직접 확인할 수 있다.

### Connection 헤더 - Keep Alive

- **비유**: 전화 통화. 질문 하나마다 전화를 끊고 다시 걸면 번거롭다. **통화를 유지한 채 여러 질문을 이어서 하는 것**이 Keep-Alive다.
- **왜 필요할까?** TCP 연결(3-way handshake)과 TLS 핸드셰이크는 시간이 걸린다. 웹 페이지 하나에 CSS·JS·이미지 등 요청이 수십 개인데, 매번 연결을 새로 맺으면 느려진다.

| 버전 | 기본 동작 | 헤더 |
|---|---|---|
| HTTP/1.0 | 요청 1번마다 연결 종료 | 연결을 유지하려면 `Connection: keep-alive`를 명시 |
| HTTP/1.1 | **연결 유지(persistent connection)가 기본** | 끊고 싶을 때 `Connection: close` |
| HTTP/2, HTTP/3 | 한 연결에서 여러 요청을 동시에 처리 | `Connection`, `Keep-Alive` 헤더 사용 금지 (연결 관리 방식이 다름) |

- `Keep-Alive: timeout=5, max=100` → 쉬고 있는 연결을 5초 동안 유지하고, 최대 100개 요청까지 이 연결로 처리하겠다는 힌트
- **장점**: 연결을 다시 맺는 시간이 줄어 빠르고, 서버·네트워크 자원도 아낀다.
- **주의**: 놀고 있는 연결도 서버 자원을 차지하므로 `timeout`으로 적당히 끊어 준다.

실습 서버에 한 번에 두 URL을 요청했을 때 실제 로그. 두 번째 요청은 **연결을 새로 맺지 않고 재사용**한다:
```bash
$ curl -v http://127.0.0.1:8000/patients/1 http://127.0.0.1:8000/patients/2
* Connected to 127.0.0.1 (127.0.0.1) port 8000
> GET /patients/1 HTTP/1.1
< HTTP/1.1 200 OK
* Connection #0 to host 127.0.0.1 left intact        <- 응답 후에도 연결을 끊지 않음
{"id":1,"name":"kim","age":30}
* Re-using existing connection with host 127.0.0.1   <- 같은 연결(#0) 재사용
> GET /patients/2 HTTP/1.1
< HTTP/1.1 200 OK
* Connection #0 to host 127.0.0.1 left intact
{"id":2,"name":"lee","age":45}
```

## 3. Network 기초

### 네트워크

- **비유**: 집(컴퓨터)들이 골목길(케이블·전파)로 이어진 동네.
- **정의**: 두 대 이상의 기기가 유선·무선으로 연결되어 데이터를 주고받는 체계.
- **규모**: LAN(집·사무실 같은 좁은 범위), WAN(도시·국가를 잇는 넓은 범위)
- **주요 장비**
  - 스위치: 같은 네트워크 안에서 MAC 주소(네트워크 장치마다 붙은 고유 번호)를 보고 데이터를 전달
  - 라우터: 서로 다른 네트워크 사이에서 IP 주소를 보고 길(경로)을 찾아 전달
  - 공유기: 가정용 라우터 + 스위치 + 와이파이 + 내부 IP 자동 배정(DHCP)·주소 변환(NAT)
- **패킷**: 데이터는 통째로가 아니라 작은 조각(패킷)으로 나뉘어 전송되고, 도착지에서 다시 합쳐진다.
- **계층 구조 (TCP/IP 4계층)**: 역할을 층으로 나눠 각 층이 자기 일만 한다.

| 계층 | 하는 일 | 예 |
|---|---|---|
| 응용 | 프로그램끼리의 약속 | HTTP, DNS, SSH |
| 전송 | 프로그램(포트)까지 전달, 신뢰성 | TCP(순서·재전송 보장), UDP(빠름, 보장 없음) |
| 인터넷 | 목적지 컴퓨터(IP)까지 경로 찾기 | IP |
| 네트워크 접근 | 실제 선·전파로 전송 | 이더넷, 와이파이 |

(이론에서는 7계층으로 더 잘게 나눈 OSI 모델도 자주 쓴다.)

### 인터넷

- **정의**: 전 세계의 수많은 네트워크를 **TCP/IP라는 공통 규칙으로 연결한 거대한 네트워크**. 'Inter-network(네트워크들 사이를 잇는 네트워크)'에서 온 말이다.
- **기원**: 1969년 미국의 ARPANET에서 시작했고, 1983년 ARPANET이 TCP/IP로 전환하면서 오늘날 인터넷의 기반이 마련되었다.
- 우리는 통신사(ISP, Internet Service Provider)를 통해 인터넷에 연결된다.
- 다시 강조: **인터넷(도로망) ≠ 웹(도로 위 서비스 중 하나)**

### IP, Port

**IP 주소** = 네트워크에서 기기를 찾아가기 위한 **건물 주소**

| 구분 | IPv4 | IPv6 |
|---|---|---|
| 길이 | 32비트 | 128비트 |
| 표기 | 점으로 구분한 0~255 숫자 4개: `192.168.0.10` | 콜론으로 구분한 16진수: `2001:db8::1` |
| 개수 | 약 43억 개 (2의 32제곱) → 부족 | 사실상 무한 |

- **공인 IP vs 사설 IP**: 인터넷에서 유일한 주소(공인) vs 집·회사 안에서만 쓰는 주소(사설). 사설 대역은 `10.x.x.x`, `172.16.x.x ~ 172.31.x.x`, `192.168.x.x`. 공유기가 NAT로 사설 IP와 공인 IP를 바꿔 준다.
- **`127.0.0.1` (localhost)**: '내 컴퓨터 자신'을 가리키는 특별한 주소. 실습 서버 주소가 이것이었다.

**Port** = 한 건물(컴퓨터) 안에서 **몇 호실(어떤 프로그램)** 로 갈지 정하는 번호 (0 ~ 65535)

| 포트 | 서비스 |
|---|---|
| 80 / 443 | HTTP / HTTPS |
| 22 | SSH (원격 접속) |
| 53 | DNS |
| 3306 | MySQL |
| 8000 | Uvicorn(FastAPI) 개발 서버 기본값 |
| 5500 | VS Code Live Server 확장 기본값 |

- 0~1023은 잘 알려진 포트(Well-known), 1024~49151은 등록된 포트, 49152~65535는 동적·임시 포트다.
- `http://localhost:8000/docs` = "내 컴퓨터(localhost)의 8000번 포트에서 돌고 있는 프로그램에게 /docs를 달라"는 뜻.
- **IP + Port 조합**(예: `127.0.0.1:8000`)으로 '어느 컴퓨터의 어느 프로그램'인지 정확히 찾아간다.

### DNS

- **DNS(Domain Name System)**: 사람이 기억하기 쉬운 **도메인 이름을 IP 주소로 바꿔 주는 시스템**. 인터넷의 전화번호부.
- **도메인 구조** (오른쪽이 상위): `www.example.co.kr`
  ```
  . (루트)  →  kr (최상위 도메인, TLD)  →  co  →  example  →  www (서브도메인)
  ```
- **조회 과정**
  ```
  (1) 브라우저·운영체제의 캐시와 hosts 파일을 먼저 확인 (최근에 찾아본 적 있으면 바로 사용)
  (2) 없으면 리졸버(통신사 DNS 또는 8.8.8.8, 1.1.1.1 같은 공용 DNS)에 질문
  (3) 리졸버가 차례로 물어봄:  루트 네임서버 → TLD(.kr) 네임서버 → example.co.kr의 권한 있는 네임서버
  (4) 받은 IP 주소를 TTL(유효시간) 동안 캐시해 두고 브라우저에 전달
  ```
- **주요 레코드 종류**

| 레코드 | 의미 |
|---|---|
| A | 도메인 → IPv4 주소 |
| AAAA | 도메인 → IPv6 주소 |
| CNAME | 도메인의 별명 (다른 도메인을 가리킴) |
| MX | 메일 서버 |
| TXT | 텍스트 정보 (도메인 소유 인증 등) |
| NS | 이 도메인을 담당하는 네임서버 |

- DNS는 주로 **UDP 53번 포트**를 쓴다 (응답이 크면 TCP 53번).
- 직접 확인해 보기: `nslookup naver.com` (Windows·macOS 공통), `dig naver.com` (macOS·Linux)
